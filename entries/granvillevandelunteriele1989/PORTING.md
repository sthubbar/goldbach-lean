# Provenance of the LeanLab files

`LeanLab/GvLtR1989/` holds the files that the Granville, van de Lune and te Riele 1989 entry
needs. AI agents, Claude by Anthropic, wrote all of them in Steve Hubbard's Lean Lab or while
packaging this entry. No code from outside the lab is included, so the repository NOTICE does
not change for this entry. Binary Goldbach is open; nothing here claims it.

## What is proved, and on what range

`LeanLab.GvLtR1989.gvltr_ratio_upTo2`: for every even n with 6 <= n <= 323740000, `minGB n`
and `n - minGB n` are prime and `minGB n < 1.603 · log² n · log log n`. Section 5 of the
paper states this bound for every even n up to 2 · 10^10, so the range here is much smaller
than the paper's, about 1.6 percent of it. The range 323740002 to 2 · 10^10 is not covered.

  `Common/Goldbach.lean`, written by Claude in October 2026; the prime lists are the lab's

* `Sieve.lean` and `Core.lean`: written by the packaging agent, Claude, on 2026-11-16, after
  the lab's bit sieve `Verifications/Top50/BitSieve.lean`. The proofs of `repL_mult`,
  `osieve_of_dvd`, `prime_of_opm` and `of_gmo` follow the lab's `testBit_rep`,
  `wsieve_of_dvd`, `prime_of_wpm` and `of_gm`.
* `Win/W000.lean` to `Win/W084.lean`, `Blk/B00.lean` to `Blk/B11.lean` and `Chain.lean`:

  primes tried in each block, the bound on p of n in each block and the decimal lower bounds
  for log n and log log n are the lab's; every one of them is checked by the kernel here.

## Changes made for this repository

* The lab proof checked each block of about 1980000 numbers with one bit vector equality whose
  sieve used `% 2 ^ W` and `Nat.log2`, over all integers in the window. The con-ron kernel that
  Palomar runs is slow on that form. The entry uses a new checker in `Core.lean`: a window
  holds only odd numbers, reduction modulo a power of two is a bitwise and with a mask, the
  doubling of each sieving pattern stops by comparing lengths instead of computing `Nat.log2`,
  and each lab block is split into two windows of about 990000 numbers, 339 windows in all.
  The soundness proofs in `Sieve.lean` are new. The window modules import only `Core.lean`,
  not Mathlib.
* The statement is stronger than the lab's `gvltr_ratio_upTo2`, which stated only the
  inequality. Because `minGB n` is 0 when n has no Goldbach partition, the inequality alone
  would not show that p of n exists; the entry's theorem also states that `minGB n` and
  `n - minGB n` are prime.
* Every file is in module syntax: the line `module`, then `public import`, the module doc
  comment and `@[expose] public section`.
* Not included: the lab's other results on this paper, among them the bound 1.25 from n = 8,
  the bound p of n <= 1321, the rows of Tables 1 to 5 and the statements of the paper's full
  range, which are cited in the lab and have no proof.
* The repository pins Lean and Mathlib v4.35.0-rc3, not the lab's v4.35.0, because Palomar's
  Challenge renderer fails on v4.35.0 and later, PalomarRegistry/PalomarSubmission issue 161.
* No file in the entry contains a placeholder proof, and no proof uses native code evaluation.

## Kernel cost

The window checks are evaluated by the kernel with `decide +kernel`. The prime lists are
checked by two walks of 10000 integers each, and the entries of `PL0` by trial division.

On a 2 core cloud sandbox with 8 GB of memory, on 2026-11-16, a `lake build` of the entry over
the prebuilt Mathlib cache took about 10 minutes, each window module 3 to 9 seconds, and the
Comparator run with the Lean kernel took 13.7 minutes and printed `Your solution is okay!`.
On the same export of the Solution, con-ron v4.35.0-rc3 with `--verified` and one worker
accepted 18496 declarations in 2187 seconds, with peak memory about 5.3 GB, and NanoDa with
two threads finished in 7.7 minutes. Palomar runs con-ron with two workers and a 30 minute
cap, so the margin is about a third if its runner is as fast as this sandbox. Sampled windows of an
earlier form of the checker, over all integers and with `Nat.log2`, ran two to three times
slower in con-ron.
